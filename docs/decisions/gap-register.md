# Gap register

The specification this build is written from admits its own incompleteness in
several hundred places, and it marks each one. This register is where those
admissions stop being admissions and become implemented decisions.

It is organised **position by position**. Every entry names one marker at one
line of one document, and the register is not a count of them. That is forced
rather than chosen: the uncertainty rule — the fourth as provided, and this
record's whole mandate — requires that an encountered marker be answered with
the marker reference, the options considered, the choice, and the rationale. A
total can carry none of those four. It can be reported, it can be compared with
another total, and it can be wrong in either direction without anybody noticing;
what it cannot do is tell a later reader which decision was taken, on what
alternatives, or why. So the unit of this record is a position, and the only way
it can be complete is by enumerating them.

| Field                               | Value                                                                                                                                                  |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Record type                         | Decision record — the register of specification incompleteness                                                                                         |
| Status                              | Operative                                                                                                                                              |
| Unit of record                      | **One marker at one line.** Positions are enumerated, never totalled                                                                                   |
| Scope                               | The five Phase-1 area documents, and nothing else                                                                                                      |
| Entry shape                         | Seven fields, every one filled on every entry                                                                                                          |
| Frames opened to author this record | **0** — every marker is in the prose, so nothing here needed the corpus                                                                                |
| Companion records                   | `docs/decisions/catalog-defects.md`, `docs/decisions/state-matrix.md`, `docs/decisions/realtime-contract.md`, `docs/decisions/component-extensions.md` |

## What this register does, and what it deliberately does not do

**It handles incompleteness. It does not handle contradiction.** Those are two
different failures of a specification and they need two different treatments. A
document that says nothing about a state has left work to be done, and the answer
is to design the state, implement it and record the judgement — which is what
every entry below does. A document that says two incompatible things has made a
claim that cannot be honoured as written, and the answer is to record the
disagreement, adopt one reading under a stated precedence order, and leave the
specification exactly as it stands. That second case belongs to
`docs/decisions/catalog-defects.md` and is not reproduced here. Where a marker
below turned out to be describing a contradiction rather than a silence, the
entry says so and names that record instead of resolving it twice.

**It owns judgements, not specifications.** An entry states what was missing,
what was weighed, what was chosen and why. It does not restate the resulting
specification, because the record that owns the specification will then have two
versions of it and they will diverge on the first edit. Presentation of a state
belongs to `docs/decisions/state-matrix.md`; the reconnect protocol belongs to
`docs/decisions/realtime-contract.md`; the decision between a new variant and a
new component identifier belongs to
`docs/decisions/component-extensions.md`. Each is pointed at, never copied.

**It resolves a structure once.** Where an entry's choice is a piece of user
interface, the structure is implemented one time in the shared component library
and the variant-or-new-contract judgement is registered in the extensions record
above, per the single-implementation rule — the first as provided. An entry here
that produced a UI structure names that record and stops.

**It claims nothing about the deferred areas.** Eighteen area documents describe
phases this run does not build. They carry markers too, and none of them is
enumerated below. The completeness claim at the end of this record is scoped
accordingly and is worth reading before the register is relied on as a survey.

## The arithmetic, recorded and not reconciled

Two figures describe how much of the specification's marked incompleteness falls
inside this run, and they do not agree.

The **planning baseline** is the census stated in the uncertainty rule itself,
which fixes the number of build-obligation markers, partial-capture notes and
gap markers across the whole specification. Of that population, roughly **111**
were estimated to fall inside this run's five Phase-1 areas, and that estimate is
what the build was planned against.

A **direct composition** over the same five documents — build-obligation
markers, partial-capture notes and inferred-content marks, counted where they
occur — measures **156**.

Both are recorded. **Neither is reconciled into the other, and neither is
asserted over the other.** They are not two attempts at one number; they answer
slightly different questions about slightly different populations, and forcing
them together would replace a visible discrepancy with an invisible choice. What
can be said without choosing is how each is composed:

| Composition over the five Phase-1 documents        | Result |
| -------------------------------------------------- | ------ |
| Build obligations + partial captures + gap markers | 111    |
| Build obligations + partial captures + inferences  | 156    |

Six of those occurrences are the vocabulary rather than the work, and because this

**The wider divergence is not this record's to settle.** More than two readings
of the census exist across the sources this build runs under, and the divergence
between them is recorded as entry 2 of `docs/decisions/catalog-defects.md`. It is
pointed at here and deliberately not restated, so that there is one account of it
rather than two that drift.

**Completeness here is established by enumeration, not by matching a total.** If
a marker below is missing, the way to find that out is to walk the five documents
and compare positions, not to add the rows up and check the answer against 111 or
against 156. That is the whole reason the register is shaped this way.

## The four registers the catalog writes in, and how to recognise one

The product overview defines the catalog's evidence registers once, at
`00-product-overview.md` L13–L17, and every area document uses them without
restating them. Three of them mark work for this register. Recognising which one
a passage is written in is the difference between reading an observation and
reading an obligation.

| Register             | How it reads                                                  | What it means for this register                                                   |
| -------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **Build obligation** | A block quote opening with the obligation label               | A requirement the corpus **cannot** evidence either way. Always an open work item |
| **Partial capture**  | A block quote opening with the partial-capture label          | A workflow or a state the corpus shows only in part. Always an open work item     |
| **Gap marker**       | A named gap, cited by the gap contract's identifier           | A surface, state or contract the corpus does not evidence, to be designed         |
| **Inference**        | An inline mark introducing a deduction, with its basis stated | A weaker signal than a marker, and still an open decision                         |

Two properties of the obligation register are stated in the definition and bear
repeating here because they decide how entries are written. **Silence is never
evidence either way** — where no gate is visible on an action, the honest
statement is that none is _visible_, not that none is required. And **an
obligation must be checkable**: it says what the build must do, not that the
build should be careful. Every `Choice` below is written to be checkable, and
every `Proved by` names where the check lives.

The fourth register deserves its own caution. An inference is not a marker; it is
a deduction the catalog drew and labelled, with the basis it drew it from. It is
weaker evidence than an observation and stronger than a silence. It is
nonetheless an open decision, because a build that treats a labelled deduction as
though it had been read from a capture has quietly promoted somebody's reasoning
to a fact. The inferences are enumerated by position in their own section, with
the load-bearing ones broken out.

The catalog carries a fifth register for a frame that could not be inspected. No
occurrence of it falls in the five Phase-1 documents, so no entry below arises
from one.

## The entry shape

Every entry in this register fills the same seven fields. An entry that cannot
fill one of them is not ready to be written.

```text
Ref                | the document and line, as `NN-name.md` L123
Class              | obligation, partial capture, gap, or inference
What is missing    | what the corpus or the prose does not settle
Options considered | the alternatives weighed, or that none applied
Choice             | the behaviour implemented, checkably stated
Rationale          | why that one and not another
Proved by          | the test that holds the build to the choice
```

Three notes on filling them:

- **`Options considered` is never empty.** Where one answer was obvious, the
  field records that no alternative was reasonable, and why. "No alternative was
  reasonable" is itself a judgement, and a reader who disagrees with it needs to
  see that it was made rather than infer it from a blank.
- **`Proved by` names a test, not an intention.** The uncertainty rule forbids
  marking a criterion satisfied without a passing test behind it, so an entry
  that claims a behaviour names where the behaviour is asserted. Where the
  assertion is a component's own co-located test, the contract is named; where it
  is a suite, the suite is named.
- **A repeated decision is cross-referenced, never restated.** Where two markers
  in different places resolve to the same choice, both positions are listed and
  the second points at the first. The position is the point of the entry; the
  rationale only needs to exist once.

the basis it drew it from, labelled so that a reader can tell it apart from an
observation. It is not a marker, and it is not silence. It is nonetheless an open
decision, because adopting a labelled deduction as though it had been read from a
capture promotes somebody's reasoning to a fact without anybody choosing to.

## The nine unevidenced state families

This is the most consequential section in the register, and the reason is that
these behaviours are required outright while nothing in the corpus can validate
any of them.

**The source material, stated honestly.** The state document ends with an explicit
inventory of the states the corpus does not show, at `21-states.md` L459–L479. Its
own framing of that inventory is the important part: each item is a state a build
will plausibly need, and **none of them is described there, because describing one
would be invention**. That is a discipline rather than an omission, and it is the
reason this register exists — the catalog refused to design them precisely so that
a build would have to, visibly and on the record. This is where they are designed.

**What is being claimed, and what is not.** Every presentation named below is
**authored**. Not one of them is a transcription, and each entry's `What is
missing` column says so. Where the corpus carries something adjacent — and in four
cases it does — the adjacent thing is recorded as a **near-miss** and never
promoted to evidence for the family it sits beside. A near-miss recorded as
evidence is the specific way this section could go wrong, so the four are named
individually below and again in the closing note.

**Where the specifications live.** Presentation belongs to
`docs/decisions/state-matrix.md`, which specifies each family's rendering and what
shape it reuses. The protocol behind the first four — backoff, cursor and replay —
belongs to `docs/decisions/realtime-contract.md`. Both are pointed at and neither
is duplicated: this register owns the **judgement**, those records own the
**specification**, and a second copy of either would be a second version of it.

### Why this family carries disproportionate weight

Reliability is required outright: reconnection with exponential backoff and
jitter, a client cursor at the highest contiguous position, and a full replay of
the gap on reconnect. All of it is specified in
`docs/decisions/realtime-contract.md` and all of it is behaviour that runs while
nothing on the screen changes — unless these states exist.

That is the whole argument. **A protocol nobody can see is a protocol nobody can
test.** Backoff is only observable if something reports that a retry is pending;
replay is only observable if something reported that the connection had gone. So
the nine authored families are not decoration added to a reliability feature —
they are the surface that makes the reliability feature checkable, which is why
they are registered here with the same rigour as an obligation that guards a
credential.

### The one thing here that is not a gap

**Focus treatment is observed, and it is specified.** The same inventory that
lists the nine families opens, at `21-states.md` L463, by recording that the focus
treatment _itself_ was captured — a ring outside a field's border with a caret
(frames 490, 491, 63, 43) and a ring retained by a control whose surface has
closed (frame 288). Three further granularities of the same treatment are observed
and are specified by the areas that own their surfaces.

It is recorded here for one reason: so that it is not designed a second time as
though it were missing. What _is_ missing at that position is narrower and is
already covered by the build's own accessibility work — the **traversal** that
produces the treatment. No capture shows two successive focus positions, a skip
link, focus containment inside an open modal, or a checkbox or radio carrying the
treatment. Tab order, containment and restoration on dismissal are therefore build
decisions, and they are asserted in `e2e/a11y.spec.ts` rather than transcribed.

One nearby treatment is **not** focus and must not be read as it: a date grid
marks the current day with an unfilled ring while earlier days render at reduced
contrast (frame 53). The state document records that as its own current-item state,
and reusing the focus ring for it — or the reverse — would merge two states the
specification holds apart.

## Where the corpus is silent and no marker exists

The uncertainty rule covers this case explicitly, and it is worth saying why it
needs covering. A marker is the catalog telling a build that something is missing.
The harder case is the one where the catalog says nothing at all — no observation,
no deduction, no marker — because there is then no signal to notice, and a build
can walk straight past a decision without ever registering that it made one.

**The standard applied is the one the rule sets: the smallest coherent behaviour
consistent with adjacent evidenced behaviour.** Three words in that phrase are
doing work, and each of them rules something out:

- **Smallest** — the least behaviour that answers the question. Not the most
  complete, not the most impressive, and not the one a comparable product happens
  to have. Every increment beyond the minimum is authored without evidence and is
  a liability the build carries silently.
- **Coherent** — it has to work as behaviour, not merely be defensible on paper. A
  submitting state that never resolves is smaller than one that resolves, and it
  is not coherent.
- **Consistent with adjacent evidenced behaviour** — the neighbouring surfaces
  constrain the answer. Where a nearby surface is observed doing something, the
  silent one does the analogous thing rather than a novel one.

These decisions are recorded in the same seven-field shape, with the `Ref` naming
the surface rather than a marker position, because there is no marker position to
name. That difference is deliberate and visible: an entry whose `Ref` is a surface
rather than a line is an entry nobody was told to write.

## Maintenance

**A row is added before the work, not after.** An implementing agent that meets a
marker adds its entry to this register first, with all seven fields filled, and
implements afterwards. Written afterwards, an entry is a report about what
happened; written first, it is the thing the implementation is held to — and the
`Proved by` field is what does the holding, which is why it cannot be filled in
later either.

Four further rules keep the register usable as it grows:

- **The `Ref` is a position, never a summary.** One document, one line. Where a
  marker spans a block, the line the marker itself sits on is the reference.
- **A repeated decision cross-references and both positions stay listed.** The
  rationale lives at the first position; the second names it. Deleting the second
  position because the reasoning is elsewhere would defeat the enumeration.
- **A contradiction goes to the defects register instead.** If the marker turns out
  to describe a specification that says two incompatible things rather than one
  that says nothing, the entry belongs in `docs/decisions/catalog-defects.md`.
- **A UI structure is resolved once.** The variant-or-new-identifier judgement is
  recorded in `docs/decisions/component-extensions.md`, and this register points at
  it rather than deciding it a second time.

## The completeness claim, stated exactly

**This register is complete with respect to the markers enumerated in the five
Phase-1 documents** — `00-product-overview.md`, `01-onboarding-and-auth.md`,
`02-channels.md`, `03-messaging-and-composer.md` and `21-states.md` — together with
the no-marker decisions recorded above.

**It makes no claim about the deferred areas.** Eighteen further area documents
carry markers of all four classes, and not one of them is enumerated here. A reader
who needs a whole-specification survey does not have one, and should not read this
record as though it were one.

Two narrower limits are worth stating in the same breath, because a completeness
claim that hides its own edges is not much of a claim:

- **Completeness is checkable by walking the documents, not by adding the rows
  up.** The two totals recorded near the top of this record disagree, and matching
  either of them would prove nothing about whether a position was missed. The
  positions are the audit trail.
- **An entry's `Proved by` names where the assertion lives, not that it currently
  passes.** The register records the judgement and the test that binds it; whether
  that test passes at any moment is reported by the pipeline and by
  `docs/decisions/ac-manifest.md`, not asserted here.

## Authoring conventions observed by this record

- **Authored prose only.** No third-party product name appears in the text, the
  headings, the file name or any reference. No message, label, heading or button
  caption is transcribed from a frame; every behaviour is described by what it does
  and where it does it.
- **Frames by number alone.** Every citation is a bare integer. No filename and no
  percent-encoded form appears anywhere, because both carry a prohibited name.
- **No frame opened.** Every marker enumerated above was resolved from catalog
  prose, which is where markers live. The corpus was not surveyed, enumerated,
  sampled or scanned, and nothing here needed it.
- **No colour value and no icon description.** Treatments are named semantically;
  the thirteen colour literals are declared once, in the token module, and
  discussed in `docs/decisions/theme-and-color.md`.
- **No sample entity names.** The conversation, person and role names visible in
  the corpus illustrate shape only. Every example here uses a description or no
  name at all.
- **No diagram.** The committed documentation-site configuration is a read-only
  input, and the fenced-block extension the documentation plugin brings claims a
  fenced block before any diagram renderer sees it — so a diagram here would
  publish as unrendered source. Tables and prose carry the same information and
  render everywhere.
- **Evidence by citation, and absence recorded as absence.** Every claim about the
  corpus names the specification line it came from. A state the corpus does not
  show is recorded as unobserved and marked authored, never presented as read from
  a capture.
- **Near-misses labelled as near-misses.** The four pieces of adjacent evidence in
  the state-families section are each named, each explained, and each explicitly
  disqualified as evidence for the family it sits beside.
- **Inconsistencies preserved.** The two census figures are recorded side by side
  and neither is reconciled into the other, so a later reader sees the discrepancy
  rather than inheriting a silent choice.
