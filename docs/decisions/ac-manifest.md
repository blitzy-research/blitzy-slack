# The acceptance-criteria manifest — 241 criteria, each with the test that must prove it

This record is what makes the specification executable. The five area documents in
this phase's scope publish 241 acceptance criteria, and every one of them is a claim
about behaviour that a running build either exhibits or does not. This manifest gives
each claim an address — the test that decides it — and a status that can only be
raised by that test passing.

Its defining property is its **ordering**, and the ordering is the whole point. This
record is written **before** any Phase-1 surface is implemented. Written afterwards it
would be a report about what happened: a list assembled by looking at the code, in
which every criterion the build happens to satisfy appears satisfied and every
criterion the build overlooked is simply absent, because nothing was ever accountable
for it. Written first it is a contract about what must happen. The 241 rows exist
before the tests do, so a criterion cannot be quietly dropped — a row with no citing
test is visible as exactly that, and stays visible until somebody writes the test.

## Why this record precedes the surfaces it governs

The uncertainty rule — the fourth as provided — closes with a single sentence that this
whole record exists to serve: an acceptance criterion may not be marked satisfied
without a passing test behind it. That sentence is easy to agree with and hard to
honour, because the failure it prevents does not look like a failure. It looks like a
build that works, a reviewer who reads the surface and finds it convincing, and a
criterion marked done on the strength of that reading. Nothing in that sequence is
dishonest. It is simply unverified, and unverified is indistinguishable from verified
right up until the behaviour is needed.

Three properties of this record follow directly, and each is a design decision rather
than a formatting choice.

- **The status column cannot express belief.** Its vocabulary is closed at three
  values, all three of which describe a test outcome. There is no value meaning
  "implemented", "looks right", "in progress" or "believed complete", because a
  vocabulary that can express those things will be used to express them.
- **Every row carries a target test.** Satisfaction always has an address, even before
  the test exists. A row whose target test has not been written yet still names where
  it will live, so the absence is a specific absence rather than an open question.
- **The rows precede the code.** A criterion cannot be retro-fitted to whatever was
  built, because the row was written from the criterion and not from the build.

A fourth property is worth stating because it is what keeps the record honest over
time: this manifest is **regenerated from the test suite**, not maintained by hand. A
hand-maintained ledger drifts silently and its drift is invisible; a generated one
drifts loudly, because regeneration produces a different file and the pipeline fails on
the difference.

## The arithmetic, verified independently

The 241 figure was not taken on trust. Counting the checklist items published in each
of the five area documents gives:

```text
00-product-overview.md        39    running total   39
01-onboarding-and-auth.md     46    running total   85
02-channels.md                61    running total  146
03-messaging-and-composer.md  57    running total  203
21-states.md                  38    running total  241
```

That sums to exactly **241**, and it agrees with both the requirement ledger and the
catalog's own Phase-1 gate. There is no discrepancy in either direction — not a
criterion counted twice, not a criterion missing, not an off-by-one anywhere.

**Because it reconciles exactly, no defect entry is warranted for scope arithmetic.**
That is worth saying plainly, because this build records catalog defects rather than
correcting them, and a reader who finds several such entries elsewhere might reasonably
expect one here. There is none. The counts agree, and an agreement recorded as an
agreement is as useful as a contradiction recorded as a contradiction.

The per-area subtotals are load-bearing rather than decorative. They are what allows a
mismatch to be **localised**: a regeneration that produces 240 rows tells a reader only
that something is wrong, while a regeneration that produces 60 rows for the channels
document tells them exactly where to look.

## The status vocabulary

Three values. No others are permitted, and the regenerator writes no others.

```text
not started   no test cites this criterion yet
test failing  a test cites this criterion and does not pass
test passing  a test cites this criterion and passes
```

`test passing` is the only value that reads as satisfied, and only a passing test may
produce it. The other two are equally honest and equally acceptable to report; what is
not acceptable is a value that describes a state of mind.

Explicitly prohibited, because each is the natural thing to reach for and each hides
the same gap: `done`, `complete`, `implemented`, `built`, `in progress`, `partial`,
`believed done`, `verified manually`, `n/a`, and any bare mark such as a tick. A
criterion that genuinely cannot be exercised by a test is not exempted by a special
value — it stays `not started` and its reason is written down, which is what the
[deferrals](#criteria-bounded-by-phase-scope) section below is for.

At the moment of authoring, **every row reads `not started`**, and that is the correct
and expected state of a precondition. The column is rewritten by `tools/ac-manifest/`
from the outcome of the most recent run, so the values in a checked-out copy describe
the last regeneration and nothing more.

## The citation form every test carries

Each test names the criterion it discharges, inline, in one fixed form:

```text
// AC: 02-channels.md L982 · frame 69
```

Two details in that line are easy to get wrong and both matter. The separator between
the line reference and the frame reference is a **middle dot**, not a hyphen, an
en-dash or a bullet. The line prefix is a **capital `L`** immediately followed by the
number, with no space and no `#`. The form must be **byte-identical** across the whole
suite, because the regenerator parses it: a citation written in a near-miss variant is
not a slightly untidy citation, it is an unparsed one, and an unparsed citation leaves
its criterion reading `not started` while a test for it sits in the tree passing.

The example above is a **real, resolvable citation** rather than an illustration.
The channels document's criteria section begins at L977, the line it cites is the
channel-name criterion a few lines below that, and frame 69 is the frame that criterion
itself cites. It is reproduced here as the worked example precisely so that nobody has
to invent one — copy this line, change the three values, leave everything else alone.

Frames are cited **by number only**. That is not a stylistic preference: every file in
the corpus carries a third-party product name in its filename, so a number is the only
form of frame reference that can appear in source, in a comment, in a test or in this
record. The number resolves to a path at run time, in one place, and nowhere else.

Where a criterion cites several frames, the citation names the one frame that the test
actually exercises the behaviour of. Where a criterion cites none, the frame reference
is omitted from the comment and the row's Frame column carries a dash.

## What this buys: regeneration from the suite

Because every test carries its criterion inline and the form is fixed, this manifest is
**derivable from the tree**. `tools/ac-manifest/` reads the citations out of the suite,
matches them against the criteria published by the five area documents, and rewrites
the tables and the subtotals. Three consequences follow.

- **It is reproducible at each reporting point** rather than hand-maintained. The
  figures reported at Phase-0 exit and at run end come from a regeneration, so they
  describe the tree at that moment.
- **Drift is a pipeline failure, not a stale document.** Regenerating in the pipeline
  and comparing against the committed copy turns "the manifest is out of date" from
  something a reader has to notice into something the build refuses to pass.
- **The tests are the authority on coverage, and this file is the view of it.** If the
  two disagree, the tests are right and this file is regenerated.

## How the governing rules bear on this record

Four of the five project rules reach this file directly. Each is summarised, not
transcribed; the full text of every rule lives in the rules document.

**A note on how they are named here.** Each rule is referred to by its subject and by
its position in the order the rules were provided — "the uncertainty rule, the fourth as
provided" — rather than by its identifier. That is not squeamishness about identifiers:
the identifiers themselves embed the third-party product name that the identity rule
prohibits from appearing in source, copy or comments, so writing them out in this file
would breach one rule in the act of citing another. Subject plus provided ordinal is
unambiguous, and every sibling decision record uses the same convention. The identifiers
are recoverable in full from the rules document.

**The uncertainty rule, the fourth as provided.** Its closing clause is this record's
mandate, and the three properties above discharge it. Its earlier clauses reach the rows
too: a criterion whose behaviour the corpus never evidenced still gets a row and still
gets a test, because uncertainty about _how_ something should look is not a licence to
leave it unbuilt. Those decisions are recorded in `docs/decisions/gap-register.md`,
position by position, and this manifest points at that register rather than restating
any of it.

**The corpus-handling rule, the third as provided.** The criteria live in read-only
documents. They are **cited, never copied, and never corrected in place**.
Every entry in the Criterion column below is therefore an **authored summary in this
record's own words**, not a transcription — enough to recognise which criterion a row
refers to, never enough to substitute for reading it. Where a criterion is malformed,
ambiguous or self-contradicting, the defect goes in
`docs/decisions/catalog-defects.md` and **the row stays**: a criterion is not deleted
for being awkward. Nothing here required opening a frame; every line number and every
frame number below was read from prose.

**The identity rule, the fifth as provided.** Frames are cited by number alone, for the
reason given above. No criterion text is transcribed, no string legible in a frame is
reproduced, no sample entity name from the corpus appears here, no colour value appears
here, and no third-party product name appears in any heading, path, link label or table
cell in this file.

**The authorization rule, the second as provided.** This rule changes where certain rows
point. Every mutation and every projection must ship with a test proving
that a **non-member** and a **wrong-role caller** are denied by the server, and that a
private resource is absent from all eight projections. A happy-path test cannot prove
either of those things, so the rows for those criteria point at the **denial, tenancy
and projection suites** — `apps/api/test/integration/authz/**`,
`apps/api/test/integration/tenancy/**` and
`apps/api/test/integration/projections/**` — and not merely at the surface that renders
the operation. Those suites in turn depend on `docs/decisions/role-matrix.md`, which
defines what a wrong role _is_; the matrix is a precondition of the denial suite, and
the denial suite is a precondition of those rows ever reading `test passing`.

The single-implementation rule, the first as provided, reaches this record indirectly but
visibly: because each component contract is implemented exactly once, a criterion about a
contract's variants or states points at that contract's **single** co-located test, and
two rows about the same contract point at the same file rather than at two.

## Where a target test lives

The Target test column carries a file path, chosen so that the test can actually decide
the criterion. The routing is deliberate rather than defaulted, and it follows six
rules.

| Criterion is about                                                                           | Target test                                                 |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| One component contract's own regions, variants or states                                     | `packages/ui/src/components/<Contract>/<Contract>.test.tsx` |
| Server logic decidable in isolation — encoding, canonicalisation, formatting                 | `apps/api/test/unit/**`                                     |
| Anything touching the database, authorization, tenancy, projections, realtime or idempotency | `apps/api/test/integration/<family>/**`                     |
| A user-visible flow, end to end, across surfaces or navigations                              | `e2e/specs/<area>.spec.ts`                                  |
| The workspace-isolation extension itself                                                     | `packages/db/test/tenancy.test.ts`                          |
| Accessibility                                                                                | `e2e/a11y.spec.ts`                                          |

Two homes sit alongside those and are named here so their appearance below is not read
as a stray: `packages/db/test/schema-placement.test.ts` decides the criteria about
**where a field is stored** — per-viewer relations rather than shared objects, and
credential artefacts as records rather than columns — because that is a question about
the schema rather than about a request; and `packages/shared/src/copy/en.test.ts`
decides the criteria about authored copy carrying no third-party identity, because all
microcopy is centralised there.

**The runner boundary, so the ledger is not misread.** The integration suite, the
end-to-end suite and the benchmark all run **outside** the default unit project: the
integration suite needs a real database in a container, the end-to-end suite needs a
running application, and neither is part of the fast feedback loop. The benchmark goes
further and runs **outside the default pipeline gate** altogether, deliberately, so
that a green pipeline stays fast. The consequence for this manifest is a prohibition:
**no criterion may be assigned to the benchmark.** A criterion whose only test lives
outside the gate is a criterion the gate does not check, which is the same as an
unchecked criterion with extra steps. The benchmark proves a performance property, and
performance properties are reported separately from criteria.

## Reading the five sections

What follows the markers below is derived from the five area documents and is
regenerable; the observations that make it readable are not, so they are collected here,
outside the generated span, where a regeneration cannot reach them.

### Product overview

The defining document, and the reason its criteria range so widely: it owns the shell's
own behaviour _and_ the cross-cutting contracts every other area resolves to by
identifier. So the thirty-nine rows below run from region geometry and rail data through
to the sixteen security contracts, the placement of every modelled field, and the
prohibition on a credential ever being a column. **Twelve of the thirty-nine point at a
server suite or at the database package rather than at a surface**, because what they
assert — authorization, isolation, storage placement, a secret's lifecycle, fidelity to a
stored value — is not something a rendering can demonstrate.

One row carries a dash in the Frame column. Criterion 29 cites no frame, because it is a
statement about the security contracts as a set rather than about anything rendered — and
a dash is recorded rather than a nearby frame guessed.

### Onboarding and authentication

Everything that happens before a session exists, the surfaces that create one, and the
invitations that extend one to somebody else. The area is unusually security-dense:
**eight of the forty-six** are about where a secret lives, how long it lives, who may
redeem it, and who may enrol against a stored policy — so those eight point at the
integration suite and at the schema-placement test rather than at the page that renders
the field.

The area's closing rows are its contract block, and the pattern recurs in every one of the
five documents: the surface criteria come first, and the contracts those surfaces must
satisfy are stated at the end.

### Channels

The largest area in this phase, and the one whose criteria cover the widest span of a
single object's life: creation through a two-step wizard, membership, per-member
personalisation, the four-tab details surface, the lifecycle from conversion through
archive and unarchive to deletion, and the browser that finds a channel in the first
place.

Its final eight criteria are a self-contained security block, and they are the clearest
case in the whole manifest of the authorization rule redirecting a row. Criterion 54
concerns every channel mutation and criterion 55 every channel projection; neither can be
proved by a test that exercises the operation successfully, so both point at the denial
and projection suites.

### Messaging and composer

The composer, the message row, and everything that posts into a conversation. Two
structural facts shape the rows. First, the area carries the pair of contracts that must
never be merged — the nine-control formatting toolbar and the seven-control action row —
so criteria 2 and 3 point at two different co-located tests, deliberately and
permanently. Second, the content and link contracts live here, so the criteria split
cleanly between component structure and server-side validation.

One row carries a dash in the Frame column. Criterion 50 concerns match-term
highlighting, which the corpus never shows being applied, so the criterion cites no frame
and the row records that absence rather than borrowing a frame from a neighbour.

### States

The cross-cutting matrix: what every surface in the build does while loading, while
empty, while refusing an entry, while read-only, and while gated. These thirty-eight
criteria are the ones most often decided by a component test, and for a structural
reason — a state is a property of a contract rather than of a flow, so it is provable
where the contract is implemented.

The exceptions are instructive. **Two** rows point at the accessibility pass, because focus
behaviour — a ring outside the border, a ring that survives a menu closing — is asserted
there. **One** points at the state module's own test, because a count of health levels is a
property of the vocabulary rather than of any one surface. **One** points at the token
module, because a claim that no state carries a colour taken from the corpus is a claim
about tokens. And the absence criteria — no loading state covering a whole surface, no
gating kind collapsing into another — point at the end-to-end specifications, because an
absence can only be proved by walking every route and finding none.

This is also the one area with **no** row pointing at a server suite, which is exactly what
a cross-cutting presentation vocabulary should look like: these criteria constrain what the
build shows, not what it permits.

Two states of this file are errors rather than things to work around: **neither marker

undefined, and writing anyway risks overwriting authored prose — the one outcome the
arrangement exists to prevent. The tool stops and says so.

### Two vocabularies, and the mapping between them

A regenerator that parses documents and reads comments can discover that a test **claims**
a criterion. It cannot discover whether that test exercises the criterion, and it cannot
discover whether it passed — it runs nothing and reads no report. So the discovery pass
speaks in two values and deliberately has no word for satisfaction, while this record's
status column speaks in three because it reports an outcome.

| Discovery pass | Status recorded here             | What it means                                                                    |
| -------------- | -------------------------------- | -------------------------------------------------------------------------------- |
| `uncovered`    | `not started`                    | No test claims this criterion                                                    |
| `cited`        | `test failing` or `test passing` | A test claims it; **which** of the two is decided by the run, never by the claim |

The important property is what the mapping refuses to do. **A citation is never promoted
to satisfaction.** `cited` is a claim about intent found in a comment, and the distance
between "a test says it covers this" and "a test covers this and passes" is exactly the
distance the uncertainty rule's closing clause is about. So a regeneration that has no
test outcomes to work from writes `not started` for what it discovered as `uncovered` and
leaves a `cited` row at its previous value rather than advancing it; only a reporting pass
holding actual outcomes may write `test passing`.

This is also why the discovery vocabulary is worth keeping narrow at two members. A third
member sitting in a parser invites a future edit to populate it from something convenient
— an assertion count, a green pipeline, a coverage percentage — and each of those is a
proxy for a passing test rather than a passing test.

Two cases decide the tool's behaviour at its edges, and they are deliberately asymmetric.

- **A criterion with no citing test: leave the row, status `not started`.** This is not an
  error and must not be treated as one. It is the normal state of a criterion before its
  test is written, and it is precisely the state the manifest exists to make visible. A
  tool that dropped such rows, or that failed the run on encountering one, would make the
  manifest unusable as a precondition — which is its entire purpose.
- **A citation matching no criterion: fail.** There is no benign reading of a citation
  that resolves to nothing. Either the document name or the line number is a typo, or a
  criterion moved and the citation was not updated, or the citation refers to a criterion
  outside this phase's five documents. All three are wrong, and all three are silent
  unless the tool is loud: an unmatched citation looks from inside the test file exactly
  like a matched one, so the test passes, the author believes a criterion is covered, and
  the row that criterion belongs to still reads `not started` with nobody wondering why.
  The run fails, naming the file and the citation.

### The reconciliation the tool enforces

After regeneration the per-area counts must be exactly:

```text
00-product-overview.md        39
01-onboarding-and-auth.md     46
02-channels.md                61
03-messaging-and-composer.md  57
21-states.md                  38
                             ---
                             241
```

A mismatch is **reported and recorded in `docs/decisions/catalog-defects.md`**, never
adjusted away. That instruction matters because the tempting fix is the wrong one: if the
tool counts sixty criteria in the channels document where this record says sixty-one, the
easy move is to write sixty and carry on, and the effect is that a criterion silently
stops being anybody's responsibility. The correct move is to fail, record what was counted
against what was expected, and find out which of the two is wrong — because either a
criterion was added to a read-only document, which cannot happen and therefore indicates a
parsing defect, or the parser's definition of a checklist item has drifted.

### Coverage, stated honestly

Two coverage targets govern this build and **they are different measures of different
things**. Reporting them as one figure, or letting one stand in for the other, is the
specific dishonesty this section exists to prevent.

| Measure                                               |   Target | What it counts                                                      |
| ----------------------------------------------------- | -------: | ------------------------------------------------------------------- |
| Criteria represented by a test, from the tables above | **100%** | Rows whose status is not `not started` — every criterion has a test |
| Line coverage in the API application                  |  **80%** | Executable lines of `apps/api` exercised by the suite               |

They are unrelated in both directions, which is what makes conflating them so easy and so
misleading. Every one of the 241 criteria could carry a passing test while `apps/api`
sits well under eighty per cent, because most of these criteria are about the client and
the shared library. Equally, `apps/api` could exceed ninety per cent while criteria go
unrepresented, because line coverage counts lines executed and not obligations discharged
— a suite can execute every line of a handler without ever asserting that a non-member is
refused.

So the two are reported as two lines, always, and the criteria figure is the one this
record is responsible for. A hundred per cent of criteria represented is the target; the
number reported is whatever regeneration produces, and the gap, if there is one, is listed
rather than rounded.

## Notes that prevent this record being misused

Four things this manifest is not for. Each has a plausible-sounding version that a
well-meaning reader will arrive at unaided, which is why each is written down.

### A criterion is never edited here to match what was built

The Criterion column is an authored summary of a criterion published in a read-only
document. It is a **pointer**, not a copy, and it may not be adjusted to describe the
implementation. If the build does something narrower than the criterion says, the answer is
not to narrow the summary; if the criterion turns out to be impossible as written, the
answer is not to soften it.

What happens instead is threefold. The row's **status stays honest** — `not started` or
`test failing`, whichever is true. The **reason is written down**, either in the deferrals
below or, where the criterion itself is defective, in
`docs/decisions/catalog-defects.md`. And the criterion in the area document is **left
exactly as it is**, because correcting the specification in place is prohibited and
because a later reader is better served by seeing the contradiction than by inheriting a
silent resolution of it.

**Deferred work is listed explicitly, with a reason.** "Not done" is not an acceptable
line on its own — not in this record and not in the ledger that reports from it. A reason
can be argued with, revisited and eventually discharged; a bare omission can only be
rediscovered.

### A criterion may have several tests, and a test several criteria

The mapping is many-to-many by nature, and forcing it to be one-to-one would distort both
sides.

- **One criterion, several tests.** Several of the criteria above assert a count — four
  loading shapes, six validation presentations, eleven menu rows in eight groups. A count
  is properly asserted case by case, so the honest discharge is several assertions, often
  in more than one file. The Target test column names the file that **decides** the
  criterion; where a second file contributes, it cites the same criterion in the same form
  and the regenerator finds both.
- **One test, several criteria.** A component test that exercises a contract's variants
  will legitimately discharge several criteria about that contract, and a flow
  specification will discharge several about that flow. Splitting them into one file per
  criterion would produce a suite that is harder to read and no more rigorous.
- **The one invariant: every criterion needs at least one citing test.** That is the
  direction the rule constrains. Nothing above may sit without an address, and a row whose
  status is `test passing` has, by construction, at least one passing test citing it.

Status is computed conservatively across a many-to-many mapping: a criterion reads
`test passing` only when **every** test citing it passes. One failing citation is enough
to take the criterion out of the satisfied set, which is the correct behaviour for a
count-style criterion where a single case has regressed.

### The Frame column carries what the criterion cites, and a dash means none

The number in the Frame column is the frame **the criterion itself cites** — read from the
prose of the area document, not chosen by anybody working on this record and not verified
by opening anything. Where a criterion cites several frames, the column carries the first,
and the citing test names whichever frame it actually exercises.

Where a criterion cites **no** frame, the column carries a dash. Two rows do:
criterion 29 of the product-overview document, which is a statement about the sixteen
security contracts as a set, and criterion 50 of the messaging document, which concerns
match-term highlighting — a behaviour the corpus never shows being applied. In both cases
the absence is **recorded as an absence**. Guessing a plausible neighbouring frame would
make the row look better and make the record worse, because a frame reference is evidence
and inventing evidence is the one thing a traceability record must never do.

### Where the unevidenced criteria get their behaviour from

Some of the criteria above describe behaviour the corpus cannot show — a state never
captured, a role never rendered, a refusal never photographed. They still have rows, they
still have tests, and their behaviour is still specified; it is simply specified somewhere
else, and this record points rather than repeats.

- `docs/decisions/gap-register.md` carries the decision behind every marked gap, position
  by position, with the options considered and the rationale. A row above whose criterion
  rests on an authored choice is discharged by a test written against that register's
  decision.
- `docs/decisions/role-matrix.md` carries the account types and the capability decisions
  that make a **wrong-role caller** constructible in the first place. Every row pointing at
  a denial suite depends on it, which is why that record is authored before those tests
  exist.
- `docs/decisions/state-matrix.md` carries the state vocabulary that the states document's
  criteria are asserted against.

Restating any of that here would create a second copy to drift from the first. The
manifest's job is to say **which test decides which criterion**, and to say nothing else
twice.

## Authoring conventions observed by this record

Stated so that a regeneration, or a later hand, keeps the properties that make this record
usable.

- **Evidence by citation.** Every row names its document and line. No claim is made about a
  criterion that its citation does not support, and no frame number appears that the
  criterion did not supply.
- **Authored summaries only.** The Criterion column is written in this record's own words.
  No criterion text is transcribed, and no string legible in a frame is reproduced.
- **Frames by number.** A bare integer, or a dash. Never a filename, never a path.
- **Zero frames opened.** Every line number and frame number in this record came from
  prose. The corpus was not opened, sampled, surveyed or enumerated to author it.
- **State only what is shown; record absence as absence.** Two rows carry a dash for that
  reason, and the deferrals above are listed rather than smoothed over.
- **Preserve inconsistencies.** Where the specification contradicts itself, the
  contradiction goes in `docs/decisions/catalog-defects.md` and the row stays. This record
  reconciles nothing silently.
- **Tables and prose only.** No diagram fences: the committed documentation configuration
  does not render them, because the extension that handles fenced blocks consumes them
  first. Fenced content is plain text and every fenced line is short enough to survive a
  narrow rendering.
- **One claim site.** Satisfaction is claimed here and nowhere else. A sibling record may
  say what must be proved; only this one says whether the test that proves it passes.
